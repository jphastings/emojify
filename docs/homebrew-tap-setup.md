# Homebrew tap publishing — GitHub App setup

`emojify` publishes a Homebrew cask to
[`jphastings/homebrew-tools`](https://github.com/jphastings/homebrew-tools) on
every tagged release, so that this works:

```console
$ brew install jphastings/tools/emojify
```

Pushing a commit to *another* repository is something the release workflow's
built-in `GITHUB_TOKEN` cannot do — that token is scoped to this repo only.
The usual workaround is a long-lived Personal Access Token stored as a secret.
We're deliberately not doing that; this uses a **GitHub App** instead.

**Status: not yet wired up.** The code in this repo is already written and
gated, so tagging a release today succeeds and simply doesn't push the cask.
Completing the steps below switches it on with no further code changes.

---

## Why a GitHub App rather than a PAT

| | Fine-grained PAT | GitHub App |
|---|---|---|
| Lifetime of the credential in CI | Long-lived (up to a year, often "no expiry") | Minted per-run, expires in ~1 hour |
| Tied to | A person's account — dies when they leave, inherits their access | The App itself |
| Scope | Whatever repos the PAT lists | Only repos the App is *installed* on |
| Rotation | Manual, and easy to forget | Only the App private key, rotated rarely |
| Audit trail | Shows as the person | Shows as the App (`emojify-release[bot]`) |

The App still needs two secrets in this repo, but they mint short-lived,
narrowly-scoped tokens rather than *being* a broad standing credential.

---

## What to do

All of this happens in the GitHub UI plus this repo's settings — nothing else
in the codebase needs to change.

### 1. Create the App

<https://github.com/settings/apps/new> (a personal-account App is fine; these
are both personal repos).

- **Name**: `emojify-release` (must be globally unique — adjust if taken; the
  name only shows up as the commit author in the tap)
- **Homepage URL**: `https://github.com/jphastings/emojify`
- **Webhook**: untick **Active**. This App never receives events.
- **Repository permissions** → **Contents: Read and write**.
  Nothing else. That single permission is all the cask push needs.
- **Where can this GitHub App be installed?** → *Only on this account*

Create it, then note the **App ID** shown on the settings page.

### 2. Generate a private key

Same settings page → **Private keys** → **Generate a private key**. A `.pem`
file downloads; GitHub does not keep a copy. Keep it safe until step 4, then
delete the local copy.

### 3. Install the App on the tap — and *only* the tap

App settings → **Install App** → your account → **Only select repositories** →
pick `homebrew-tools` alone.

> Do not select "All repositories". The whole point is that a leaked token from
> this workflow can write to the tap and nothing else.

### 4. Add the credentials to *this* repo

In `jphastings/emojify` → Settings → Secrets and variables → Actions:

- **Variables** tab → New variable
  - Name: `HOMEBREW_TAP_APP_ID`
  - Value: the App ID from step 1

  (A variable, not a secret — the workflow tests it with
  `if: vars.HOMEBREW_TAP_APP_ID != ''` to decide whether to run at all, and
  secrets aren't readable in a step-level `if`. An App ID isn't sensitive.)

- **Secrets** tab → New repository secret
  - Name: `HOMEBREW_TAP_APP_PRIVATE_KEY`
  - Value: the entire contents of the `.pem` from step 2, including the
    `-----BEGIN…` and `-----END…` lines

Then delete the local `.pem`.

### 5. Verify

Tag a release (or re-run the last release workflow). In the **Release** run you
should see the `tap-token` step execute rather than skip, and goreleaser log a
`homebrew cask` publish. Then:

```console
$ brew update
$ brew install jphastings/tools/emojify
$ echo "happy birthday!" | emojify
🥳
```

A new `Casks/emojify.rb` should appear in the tap, authored by the App.

## How it's wired here

- **`.goreleaser.yaml`** → `homebrew_casks:` block. Note `skip_upload` is
  templated on the token: empty token ⇒ the cask is still *generated* (you can
  inspect it under `dist/homebrew/Casks/`) but not pushed. That's what makes
  releases safe before this setup is done.
- **`.github/workflows/release.yml`** → the `tap-token` step uses
  [`actions/create-github-app-token`](https://github.com/actions/create-github-app-token)
  to exchange the App ID + private key for an installation token scoped to
  `homebrew-tools`, and passes it to goreleaser as `HOMEBREW_TAP_TOKEN`.

## Notes and gotchas

- **It's a cask, not a formula.** GoReleaser's `brews:` block is deprecated and
  now fails `goreleaser check` outright; `homebrew_casks` replaces it. The
  existing `Formula/*.rb` files in the tap were generated by older GoReleaser
  versions and still work — this just lands in `Casks/` instead.
- **Linux.** The generated cask includes `on_linux` URLs, but cask support on
  Homebrew-for-Linux is patchy. Treat macOS as the supported path here; Linux
  users have `go install`, the release archives, and the container image.
- **The cask ships the pure-Go model.** GoReleaser builds with `CGO_ENABLED=0`
  and no `onnx` tag, so `brew install` gets the small, dependency-free
  embedder — noticeably less sharp than the ONNX model the container runs.
  The cask's `caveats` says so on install.
- **Quarantine.** These binaries aren't signed or notarized, so the cask has a
  `postflight` hook clearing `com.apple.quarantine`; without it Gatekeeper
  blocks the binary on first run.
- **Other repos.** The same App can be installed for other tools that publish
  to this tap — install it on their repos too and add the same variable/secret
  pair there. One App, many publishers, still only tap write access.
